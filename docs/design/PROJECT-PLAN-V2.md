## 1. 项目愿景

### 1.1 问题陈述

Linux 内核和驱动开发者面临的核心痛点：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                          │
│  问题：理解大型代码库的函数执行流程                                       │
│                                                                          │
│  场景1：调试一个复杂的 USB 驱动                                          │
│  ────────────────────────────────────────                               │
│  • 代码量：5000+ 行                                                     │
│  • 异步机制：workqueue、timer、irq、threaded irq                        │
│  • 回调嵌套：probe → INIT_WORK → handler → completion                   │
│  • 困难：不知道函数什么时候被调用、调用链路是什么                         │
│                                                                          │
│  场景2：维护遗留驱动                                                    │
│  ────────────────────────────────────────                               │
│  • 没有文档                                                             │
│  • 没有注释                                                             │
│  • 不知道修改一个函数会影响哪些地方                                      │
│                                                                          │
│  现有工具的不足：                                                        │
│  • source insight / VSCode: 只能静态跳转，不能追踪执行流程              │
│  • ftrace: 需要真机运行，不能离线分析                                    │
│  • gdb: 需要运行时调试，不能提前分析                                     │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.2 解决方案

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          FlowSight 解决方案                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  愿景：不运行代码，就能精准知道函数执行过程                               │
│                                                                          │
│  核心能力：                                                              │
│  • 静态分析：提取调用关系、结构信息                                      │
│  • 符号执行：遍历所有执行路径，生成约束条件                               │
│  • AI辅助：翻译业务语义，解释触发时机                                    │
│  • 自学习：从用户反馈中持续改进                                          │
│                                                                          │
│  用户体验：                                                              │
│  1. 在 IDE 中打开函数                                                    │
│  2. 点击"分析执行流程"                                                  │
│  3. IDE 直接展示 ftrace 风格的执行流                                     │
│  4. 用户不需要追问任何问题                                               │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.3 差异化定位

| 维度 | 传统 IDE | ftrace/LTTng | FlowSight |
|-----|----------|--------------|-----------|
| 运行方式 | 不需要运行 | 需要真机运行 | 不需要运行 |
| 静态分析 | ✅ 基本 | ❌ | ✅ 深度 |
| 符号执行 | ❌ | ❌ | ✅ |
| AI 辅助 | ❌ | ❌ | ✅ 本地模型 |
| 执行流展示 | ❌ | ✅ | ✅ ftrace 风格 |
| 离线使用 | ✅ | ❌ | ✅ |
| 本地部署 | ✅ | ❌ | ✅ |

### 2.1 主要用户群体

| 用户群体 | 典型场景 | 核心需求 |
|---------|---------|---------|
| **Linux 驱动开发者** | 开发 USB/I2C/PCI 驱动 | 理解回调机制、异步调用 |
| **内核子系统维护者** | 维护 VFS/networking 子系统 | 追踪跨模块调用链 |

```

├── 自学习机制
└── 跨平台支持

P2（可以做）：
├── Android 框架支持
├── 多架构支持（ARM/x86/RISC-V）
└── 云端协作功能
```

## 3. 核心功能

### 3.1 功能列表

#### F1: 静态调用关系分析

```
功能描述：
  提取函数之间的调用关系，构建调用图

技术方案：
  • Tree-sitter 解析 C 代码 AST
  • 识别函数调用、宏调用
  • 跨文件分析（需要完整的代码索引）

输出：
  • 调用图（有向图）
  • 函数定义位置
  • 调用位置列表
```

#### F2: 回调函数识别

```
功能描述：
  识别注册到内核框架的回调函数（probe/disconnect/handler 等）

技术方案：
  • 模式匹配：INIT_WORK、request_irq 等
  • Ops 表解析：file_operations、usb_driver 等
  • 知识库补充：内核调用链

输出：
  • 回调函数列表
  • 绑定类型（workqueue/irq/ops）
  • 触发条件
```

#### F3: 异步机制追踪

```
功能描述：
  追踪异步执行流程（workqueue、timer、tasklet、softirq）

技术方案：
  • 识别 INIT_WORK、timer_setup 等绑定模式
  • 识别 schedule_*、tasklet_schedule 等触发模式
  • 知识库补充完整的异步调用链

输出：
  • 异步回调关系图
  • 触发时机说明
  • 执行上下文（进程/软中断/硬中断）
```

#### F4: 符号执行路径分析

```
功能描述：
  使用符号执行遍历所有执行路径，生成精确的分支条件

技术方案：
  • KLEE 符号执行引擎
  • 约束条件生成
  • 路径爆炸控制

输出：
  • 所有可能的执行路径
  • 每条路径的分支条件
  • 具体的参数值（测试用例）
```

#### F5: AI 条件翻译

```
功能描述：
  使用本地 AI 模型将代码条件翻译为业务语义

技术方案：
  • 本地 1.3B 模型（llama.cpp）
  • 非对话模式，直接生成 JSON
  • 知识库辅助

输出：
  • if (x > 0) → "设备忙碌时"
  • if (ret == -ENODEV) → "设备不匹配"
```

#### F6: ftrace 风格执行流展示

```
功能描述：
  在 IDE 中展示类似 ftrace 的执行流

技术方案：
  • 文本视图：缩进 + 深度指示器
  • 图形视图：React Flow 节点
  • 交互式：折叠/展开、跳转

输出示例：
  ════════════════════════════════════════════════════════
   0)               |  my_probe() {
   0)   ========    |    kzalloc()
   0)   ========    |    usb_set_intfdata()
   0)   ========    |    register_device()
   0)               |  }
   0)               |
   0)  async        |  INIT_WORK(&dev->work, work_handler)
   0)  ----         |    → work_handler() [WorkQueue]
  ════════════════════════════════════════════════════════
```

#### F7: 自学习机制

```
功能描述：
  从用户反馈中持续学习和改进

技术方案：
  • 用户反馈收集（正确性、知识补充、新模式）
  • 本地 LoRA 增量训练
  • 匿名知识上传（可选）

输出：
  • 用户专用的 LoRA 适配器
  • 更准确的分析结果
  • 改进全局模型（间接）
```

## 7. 风险与应对

### 7.1 技术风险

| 风险 | 可能性 | 影响 | 应对措施 |
|-----|-------|------|---------|
| 符号执行路径爆炸 | 高 | 中 | 限制路径数量，超时控制 |
| 本地模型质量不足 | 中 | 高 | 知识库补充，持续自学习 |
| KLEE 集成困难 | 中 | 高 | 评估 alternatives (angr/manticore) |
| 内存不足 | 低 | 高 | 增量分析，分块处理 |

### 7.2 项目风险

| 风险 | 可能性 | 影响 | 应对措施 |
|-----|-------|------|---------|
| 进度延期 | 中 | 中 | 优先级排序，MVP 优先 |
| 需求变更 | 中 | 中 | 敏捷开发，快速迭代 |
| 资源不足 | 低 | 高 | 预留缓冲，简化方案 |

### 7.3 缓解策略

```
风险缓解总体策略：
1. MVP 优先：先实现核心功能，再迭代增强
2. 技术验证：每个新技术先 POC，再大规模使用
3. 渐进交付：每个 Phase 都有可运行的版本
4. 回退计划：保留简单方案作为备选
```
